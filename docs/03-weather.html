Weather Module — Build Instructions

A phone-first forecast card for a dated event. Free data, no API key, two display states, one tap-to-expand interaction, and a colour system where a single classification drives both the text colour and the card trim. Everything on this page is rendered with the real component CSS — the specimens are the component, not pictures of it.

The design brief in one line. A group trip has one weather question — “is the thing we planned going to suck?” — so the card answers it in plain language first (a verdict phrase), shows the numbers second, and hides the hour-by-hour detail behind a tap. Everything below serves that ordering.

1 · Data source and contract

Open-Meteo. Free, no key, no attribution requirement, 16-day forecast horizon. One request returns current conditions, daily rollups and hourly rows together, so the whole card is a single fetch.

https://api.open-meteo.com/v1/forecast
  ?latitude=36.1627&longitude=-86.7816
  &current=temperature_2m,apparent_temperature,weather_code,relative_humidity_2m,wind_speed_10m
  &daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_probability_max
  &hourly=temperature_2m,precipitation_probability,weather_code
  &temperature_unit=fahrenheit&wind_speed_unit=mph&precipitation_unit=inch
  &timezone=America/New_York&forecast_days=16

Two things matter about the shape of the response. Daily arrays are parallel — daily.time[i] lines up with daily.weather_code[i] and the rest — so you zip them into day objects before rendering. Hourly time values are local ISO strings like 2027-06-12T14:00, which means you can filter a day with a plain startsWith(date) and read the hour with slice(11,13). No timezone maths anywhere in the client, because timezone= already localised it.

Proxy it server-side with a TTL cache. The client calls your own /api/weather, never Open-Meteo directly. That gives you one upstream call per TTL window instead of one per visitor per page-load, it keeps the browser off a third-party origin, and it gives you a place to degrade gracefully:

app.get('/api/weather', async (req, res) => {
  const now = Date.now()
  if (weatherCache.data && now - weatherCache.at < WEATHER_TTL) {
    return res.json(weatherCache.data)
  }
  try {
    const r = await fetch(url, { signal: AbortSignal.timeout(8000) })
    if (!r.ok) throw new Error('open-meteo ' + r.status)
    const data = await r.json()
    weatherCache = { at: now, data }
    res.json(data)
  } catch (e) {
    // Serve a stale cache if we have one; otherwise let the client fall back.
    if (weatherCache.data) return res.json(weatherCache.data)
    res.status(502).json({ error: 'weather unavailable' })
  }
})

Stale-on-error is the important half. A forecast from forty minutes ago is vastly better than an error state, and nobody can tell the difference. The client refetches on an interval (30 * 60 * 1000) with an alive flag so an unmounted component never calls setState.

WMO weather codes become a label and an emoji through one lookup table with a fallback, so an unmapped code degrades to ['—', '🌡️'] instead of blank:

2 · The two display states

This is the part that answers “what did it look like seven days out?”. The card has exactly two modes and it picks between them by asking a single question: are any of my event dates inside the forecast window yet?

const tripDays   = allDays.filter(d => TRIP_DATES.includes(d.date))
const showingTrip = tripDays.length > 0
const days = showingTrip ? tripDays : allDays.slice(0, 7)

No countdown arithmetic, no “days until” variable, no manual switch to flip. The API’s own horizon decides. With forecast_days=16, the first event day appears in the response about fifteen days out, at which point the strip changes over on its own. Nothing else in the component branches on it.

State A — outside the window (a week or more out)

Label reads THE NEXT WEEK. The strip is allDays.slice(0, 7) — a rolling seven-day preview starting today. Underneath sits a one-line note that tells you when the real answer arrives, so the emptiness is explained rather than just absent.

State A · light · 7 days out

The strips above are live — swipe or drag them sideways. Three cards sit in view; the fourth peeking at the edge is what tells you there are more.

State B — inside the window (event days in range)

Label becomes THE TRIP, DAY BY DAY. The strip is now only the event days — four cards, not seven, not sixteen. Everything outside the trip is dropped, because once the trip is forecastable nobody cares what Tuesday looks like. The mini-note disappears, since its job is done.

State B · light · trip in range
Why the same card does both. The alternative — hide the module until the trip is close — costs you the whole pre-trip period, which is exactly when people are checking obsessively and have nothing to look at. A rolling week keeps the card alive and useful, and the transition to trip-mode happens silently one morning without anyone shipping anything.

3 · The tap-to-expand hourly panel

One piece of state, one handler:

const [selDay, setSelDay] = useState(null)
...
<button onClick={() => setSelDay(sel ? null : d.date)}>

Which produces accordion behaviour without any accordion code:

GestureResult
Tap a closed dayselDay becomes that date. The hourly panel appears below the strip. The tapped card gets the selected treatment.
Tap the same day againsel is true, so it sets null. The panel disappears, the card returns to normal. This is the “click it again to resolve it” half — same target, no separate close control, no X to hunt for.
Tap a different dayStraight swap. The panel stays open and its contents change in place; selection moves. There is never a moment with two days open or with the panel closing and reopening.
The one structural decision that makes this work. The hourly panel renders after the whole carousel — <Hourly data={data} date={selDay} /> is a sibling of the strip, not a child of a card. If you nest it inside the tapped card you get a horizontally-scrolling container trying to hold a full-width expanding panel, the strip’s layout fights you, and switching days animates as close-then-open. One panel, fixed position below the strip, contents swapped by the selected date: no layout shift in the strip at all, and the expansion always appears in the same place so your eye never has to find it.

Selected-card treatment

.wcard-sel { border-color: var(--gold) !important; background: rgba(245,197,24,0.08); }

Two changes only: the border goes full brand-gold and the fill picks up an 8%-opacity gold wash. The !important is deliberate and load-bearing — it has to beat the verdict trim colour (section 5), which is set by a class of equal specificity. Selection outranks classification: while a card is open, its border means “this one”, not “stormy”.

What’s inside the panel

const hr = Number(h.time[i].slice(11, 13))
if (!h.time[i].startsWith(date)) continue
if (hr < 8 || hr % 2 !== 0) continue

Eight slots: 8A, 10A, 12P, 2P, 4P, 6P, 8P, 10P. Two-hour steps from 8am to 10pm, everything before 8am dropped. A full 24-row hour table is a data dump — this is one glance that answers the actual question, which is “is the rain at tee time or after dark?”. Each slot stacks four lines: hour label, condition emoji, temperature, precipitation chance.

The hour formatter is compact on purpose — 8A, 12P, 2P — because eight columns across a phone leaves roughly forty pixels each:

const fmtHr = hr => (hr === 12 ? '12P' : hr < 12 ? hr + 'A' : (hr - 12) + 'P')

Precipitation gets a threshold rather than a gradient: at or above 40% the figure turns rain-blue and bold via .hourly-pop.wet; below that it stays muted grey. Scanning the row, your eye lands on the wet hours immediately. A continuous colour ramp would make you read all eight numbers to find the bad ones. Empty values render as an empty string inside a min-height: 13px box so rows never jump.

The panel itself is styled as a recess, not a card: --bg-2 fill, 1px --line border, 12px radius — one radius step tighter than the 14px day cards, which reads as nested. It’s visibly a drawer that opened underneath, not a second card competing with the strip.

4 · The verdict engine

The feature that makes the card feel like it has an opinion. Every day gets a plain-language phrase in place of — not in addition to — the usual condition label.

function verdictFor(key, code, heat, pop) {
  let cat
  if (code >= 95 || (pop != null && pop >= 70))                 cat = 'storm'
  else if (heat >= 93)                                          cat = 'hot'
  else if ((code >= 51 && code <= 67) ||
           (code >= 80 && code <= 82) ||
           (pop != null && pop >= 40))                          cat = 'rain'
  else if (heat >= 85)                                          cat = 'warm'
  else if (code <= 1)                                           cat = 'nice'
  else                                                          cat = 'meh'
  const list = VERDICTS[cat]
  return { cat, text: list[hash(key) % list.length] }
}

The order is the design. It’s a priority cascade, not a scoring function: storms outrank heat, heat outranks rain, rain outranks merely-warm. A 95° thunderstorm day is a storm day. The card leads with the nastiest true thing about the day, which is how a person would describe it.

hotheat ≥ 93°FProperly hot · Scorcher · Shade weather · Surface of the sun

heat is “the temperature that matters for is this nasty” — apparent (feels-like) temperature for the current-conditions row, daily high for the forecast cards. Rewrite the phrase pools in your own voice; the thresholds are the only part worth copying literally, and even those want a nudge for a different climate. In a dry climate the hot threshold moves up; in a mild one 85 isn’t warm.

Deterministic phrase selection

function hash(str) {
  let h = 0
  for (let i = 0; i < str.length; i++) h = (h * 31 + str.charCodeAt(i)) | 0
  return Math.abs(h)
}
// ...
list[hash(key) % list.length]

Do not use Math.random() here. The key is the date string, so a given day always draws the same phrase. Without this the card reshuffles its jokes on every React re-render — scroll away, come back, Saturday is now “Biblical” instead of “Ark weather”. That reads as a bug to the user and destroys the illusion that the app has a considered opinion. Same input, same output, every render, every device.

5 · Colour coordination

The rule, and there is only one: a single classification drives every colour decision. verdictFor returns a cat string, and both class names are built from it — nothing else in the component picks a colour.

/* forecast card: category → border trim */
<button className={'wcard verdict-border-' + v.cat + (sel ? ' wcard-sel' : '')}>

/* current conditions: category → text colour */
<div className={'wn-verdict verdict-' + nowVerdict.cat}>{nowVerdict.text}</div>

The two rows use the category differently on purpose. The right-now line is a single statement with room to shout, so the phrase itself is coloured — 17px, weight 900, full verdict hue. The forecast cards keep their phrase in plain --text and carry the colour in the border instead: seven coloured phrases in a row at 11px is confetti, and the border says the same thing at a glance without asking you to read anything. One category, one colour, applied where it reads best. There’s no second lookup to keep in sync, and adding a category means adding two adjacent CSS rules.

Three deliberate choices in that table.

Borders are the same hue at 40–55% alpha, not a separate palette. The trim is a quiet echo of the label — enough to make the strip’s shape legible while scrolling past, never loud enough to compete with the text it’s repeating. One hue per category, two intensities.

meh gets no border rule at all, so it keeps the default --line. It’s the only category where the absence is the message: a grey nothing-day has nothing to flag, and flagging it would flatten the signal on the days that do. If every card is trimmed, no card is trimmed.

Light mode is re-inked, not inverted. The same semantic colours get genuinely different hex values — dark mode’s #8fb8ff storm blue has roughly 1.4:1 contrast on cream, so light mode uses #2f5faf instead. Every light value is chosen to clear WCAG AA (4.5:1 for small text) against #f6f1e2. The category names stay identical; only the values behind them change, so no component code knows which theme is active.

One extra light-mode fix, easy to miss: emoji glyphs wash out on cream, so they get their edges re-inked.

html[data-theme='light'] .hourly-emoji,
html[data-theme='light'] .wcard-emoji {
  filter: drop-shadow(0 1px 1.5px rgba(37, 30, 13, 0.5));
}

Sun and cloud glyphs are the sky-story at a glance — the whole point of the strip — and on a pale background a yellow sun on white essentially disappears. A soft dark shadow restores the silhouette without tinting the glyph.

Non-verdict colour in the card

Temperature highs use brand gold (--gold-2) with font-variant-numeric: tabular-nums so digits don’t jitter between renders. Lows use --muted at a smaller size — present, subordinate, never scanned first. Daily precipitation chance uses --v-rain regardless of category, because 💧 40% means the same thing on a hot day as on a stormy one. That’s the one place a colour is not verdict-driven, and it’s intentional: it’s a measurement, not a judgement.

Inside a day card the vertical order is day-of-week → date → emoji → verdict → hi/lo → precip. Identity first, picture second, opinion third, numbers last. The verdict slot carries min-height: 28px with flex centring so one-line and two-line phrases produce identical card heights — without it, “Toasty” next to “Shirt-sticking weather” gives you a ragged strip.

7 · Failure and loading states

Three states, and the fallback is the one worth stealing. Loading shows a single muted line (“Checking the skies…”) — no skeleton, because the card is short enough that a skeleton is more visual noise than the content. If the fetch fails and there’s no cached data, the card renders hardcoded prose about what that place is typically like at that time of year: “mid-August in the city is hot and humid, highs around 90, afternoon thunderstorms are common.” Always true, never wrong, infinitely better than an error. And if data ever arrives, it simply replaces it.

8 · Porting checklist

StepWhat to change
1Latitude / longitude / timezone in the proxy URL.
2Your event dates as an array of YYYY-MM-DD strings (the TRIP_DATES equivalent). This is the only thing that drives the state switch.
3Phrase pools — rewrite entirely in your own voice. Keep 3–5 per category so the hash has something to pick from.
4Thresholds (93 / 85 / 70% / 40%) if your climate differs.
5The six verdict colours in both themes. Keep the semantic names; check the light values against your own background for AA.
6The fallback prose for your place and season.

Five things not to change. Deterministic phrase selection (never Math.random()). The hourly panel as a sibling of the strip, not a child of a card. scroll-padding matching the negative margin. One category driving both text and border. And meh getting no border.

import { useEffect, useState } from 'react'
import { getWeather } from '../api.js'
import { TRIP_DATES, describeWeather } from '../constants.js'

const VERDICTS = {
  storm: ['Bring the jacket', 'Ark weather', 'Biblical', 'Poncho o’clock', 'Gonna get wet'],
  hot:   ['Properly hot', 'Scorcher', 'Shade weather', 'Surface of the sun'],
  warm:  ['Toasty', 'A warm one', 'Shirt-sticking weather'],
  rain:  ['Soggy', 'Damp and grumpy', 'Umbrella day'],
  nice:  ['Chef’s kiss', 'Actually perfect', 'Golf weather', 'Patio weather'],
  meh:   ['Grey but fine', 'Meh skies', 'Nothing to report']
}

function hash(str) {
  let h = 0
  for (let i = 0; i < str.length; i++) h = (h * 31 + str.charCodeAt(i)) | 0
  return Math.abs(h)
}

// heat = the temperature that matters for "is it nasty" (feels-like now, or the daily high).
function verdictFor(key, code, heat, pop) {
  let cat
  if (code >= 95 || (pop != null && pop >= 70)) cat = 'storm'
  else if (heat >= 93) cat = 'hot'
  else if ((code >= 51 && code <= 67) || (code >= 80 && code <= 82) || (pop != null && pop >= 40)) cat = 'rain'
  else if (heat >= 85) cat = 'warm'
  else if (code <= 1) cat = 'nice'
  else cat = 'meh'
  const list = VERDICTS[cat]
  return { cat, text: list[hash(key) % list.length] }
}

// The expanded day: 8 AM to 10 PM in 2-hour steps — one glance,
// "is the rain at tee time or after dark." A 24-row hour table would be
// overcomplicating it; this answers the actual question.
function Hourly({ data, date }) {
  const h = data?.hourly
  if (!date || !h?.time) return null
  const slots = []
  for (let i = 0; i < h.time.length; i++) {
    if (!h.time[i].startsWith(date)) continue
    const hr = Number(h.time[i].slice(11, 13))
    if (hr < 8 || hr % 2 !== 0) continue
    slots.push({
      hr,
      temp: Math.round(h.temperature_2m[i]),
      pop: h.precipitation_probability?.[i],
      emoji: describeWeather(h.weather_code[i])[1]
    })
  }
  if (!slots.length) return null
  const fmtHr = hr => (hr === 12 ? '12P' : hr < 12 ? hr + 'A' : (hr - 12) + 'P')
  return (
    <div className="hourly">
      {slots.map(s => (
        <div className="hourly-slot" key={s.hr}>
          <div className="hourly-hr">{fmtHr(s.hr)}</div>
          <div className="hourly-emoji">{s.emoji}</div>
          <div className="hourly-temp">{s.temp}°</div>
          <div className={'hourly-pop' + (s.pop >= 40 ? ' wet' : '')}>
            {s.pop != null ? s.pop + '%' : ''}
          </div>
        </div>
      ))}
    </div>
  )
}

export default function Weather() {
  const [data, setData] = useState(null)
  const [failed, setFailed] = useState(false)
  // Which day card is expanded (its date string), or null. Tap to open,
  // tap again to close, tap another to switch — accordion rules.
  const [selDay, setSelDay] = useState(null)

  useEffect(() => {
    let alive = true
    async function load() {
      try {
        const w = await getWeather()
        if (alive) { setData(w); setFailed(false) }
      } catch {
        if (alive) setFailed(true)
      }
    }
    load()
    const iv = setInterval(load, 30 * 60 * 1000)
    return () => { alive = false; clearInterval(iv) }
  }, [])

  if (failed && !data) { /* hardcoded seasonal prose card — always true, never wrong */ }
  if (!data) { /* "Checking the skies…" */ }

  const cur = data.current || {}
  const [curLabel, curEmoji] = describeWeather(cur.weather_code)
  const nowVerdict = verdictFor('now', cur.weather_code, cur.apparent_temperature, null)

  const daily = data.daily || {}
  const allDays = (daily.time || []).map((date, i) => ({
    date, code: daily.weather_code?.[i],
    hi: daily.temperature_2m_max?.[i], lo: daily.temperature_2m_min?.[i],
    pop: daily.precipitation_probability_max?.[i]
  }))
  // Show the trip days once they're in range; until then, a rolling next week.
  const tripDays = allDays.filter(d => TRIP_DATES.includes(d.date))
  const showingTrip = tripDays.length > 0
  const days = showingTrip ? tripDays : allDays.slice(0, 7)

  return (
    <div className="card weather">
      <div className="card-title">🌡️ the city weather</div>

      <div className="weather-strip-label">Right now</div>
      <div className="weather-now">
        <div className="wn-emoji">{curEmoji}</div>
        <div className="wn-temp">{Math.round(cur.temperature_2m)}°</div>
        <div className="wn-meta">
          <div className={'wn-verdict verdict-' + nowVerdict.cat}>{nowVerdict.text}</div>
          <div className="wn-sub">
            {curLabel} · feels {Math.round(cur.apparent_temperature)}° ·{' '}
            {Math.round(cur.relative_humidity_2m)}% humidity
          </div>
        </div>
      </div>

      <div className="weather-strip-label">
        {showingTrip ? 'The trip, day by day' : 'The next week'}
        <span className="weather-strip-hint"> · tap a day for hourly</span>
      </div>

      <div className="weather-carousel">
        {days.map(d => {
          const [label, emoji] = describeWeather(d.code)
          const v = verdictFor(d.date, d.code, d.hi, d.pop)
          const day = new Date(d.date + 'T12:00:00')
          const dow = day.toLocaleDateString('en-US', { weekday: 'short' })
          const md = day.toLocaleDateString('en-US', { month: 'short', day: 'numeric' })
          const sel = selDay === d.date
          return (
            <button
              className={'wcard verdict-border-' + v.cat + (sel ? ' wcard-sel' : '')}
              key={d.date}
              onClick={() => setSelDay(sel ? null : d.date)}
            >
              <div className="wcard-dow">{dow}</div>
              <div className="wcard-date">{md}</div>
              <div className="wcard-emoji" title={label}>{emoji}</div>
              <div className="wcard-verdict" title={label}>{v.text}</div>
              <div className="wcard-temps">
                <span className="wcard-hi">{Math.round(d.hi)}°</span>
                <span className="wcard-lo">{Math.round(d.lo)}°</span>
              </div>
              {d.pop != null && <div className="wcard-pop">💧 {d.pop}%</div>}
            </button>
          )
        })}
      </div>

      {/* Sibling of the carousel, NOT a child of a card. This is load-bearing. */}
      <Hourly data={data} date={selDay} />

      {!showingTrip && (
        <p className="weather-mini-note">Jun 10–13 forecast drops in about two weeks out.</p>
      )}
    </div>
  )
}
